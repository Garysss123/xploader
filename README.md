# xploader v1.0

A native boot manager for the **Sony Xperia Z5 E6653 (sumire)**, inspired by the HTC HD2's MAGLDR and cLK.

xploader provides an on-device boot menu, SD folder multiboot and SD recovery boot. The goal is to make the Z5 a convenient OS development device: keep the manager separate from the replaceable eMMC OS, and keep experimental systems on the SD card.

**Developer preview — E6653 only.** The project has been tested on one unlocked E6653. Other Z5 variants and firmware layouts are unverified. This repository contains the pinned v1.0 native source, core, clean carrier builder and installer source. The core `.bin` is **not** a flashable Android boot image. See [installation and fastboot instructions](docs/INSTALL.md) before flashing.

## Features

- **Boot eMMC** — load the replaceable OS boot image from the separate OS boot partition in the tested split layout.
- **Boot SD** — boot the folder saved in `Service → Boot Settings → AD SD Dir`.
- **TWRP** — load `/twrp.img` directly from the SD root. Recovery stays on SD when the eMMC OS is replaced.
- **QuickBoot** — choose eMMC, the selected SD folder, or TWRP as the automatic boot target.
- **Always Menu** — stay in the menu until an option is selected. Hold Power during startup to override QuickBoot; release it once the menu appears.
- **PC SD Access** — expose the SD card to a PC over USB mass storage, without removing it from the phone.
- **Sony S1 Fastboot**, **Reset** and **PowerOff**.
- **Tools** — Boot Once, Payload Info, Storage Info, Boot Log, Rescue, Reset Settings and About.

Use **Volume Up/Down** to move and **short-press and release Power** to select. Native loader touch input is outside the current scope. English is the documented interface.

## SD multiboot

Use an **exFAT** SD card. The tested card is 200 GB; this is not a minimum or a guarantee for every card. Some system image files exceed FAT32's 4 GB file limit. ext4 filesystems can live **inside image files** on exFAT; a separate ext4 SD partition is unnecessary for the supplied test profiles.

```text
SD root/
├── twrp.img
├── xploader.cfg             # saved menu settings
├── lineageos19/
│   ├── startup.txt
│   ├── boot.img
│   ├── system.img
│   ├── data.img
│   └── cache.img
├── postmarketos/             # split kernel, initrd, DTB and root image
└── sailfishos/               # split kernel, initrd, DTB and root image
```

1. Extract an **xploader-adapted SD system** into its documented folder at the card root.
2. Open `Service → Boot Settings → AD SD Dir` and select that folder.
3. Return to the main menu and select **Boot SD**. The folder selection remains saved for later boots.
4. To boot automatically, use `Service → Boot Settings → QuickBoot → Boot SD`. Use **Always Menu** to restore the menu at startup.

Both an Android v0 `boot.img` and separate kernel/initrd/DTB files are supported by the current Linux profiles. [Payload examples and limits](docs/SD_BOOT.md) explain the descriptor format. There is no per-ROM hash registration or model allowlist in the SD boot menu. Payload format, bounds and the supported entry ABI still apply. A normal ROM installation ZIP needs SD adaptation; copying an arbitrary ZIP or kernel into a folder does not create a working SD system.

## Surviving ordinary ROM flashing

The tested persistent layout keeps the original Sony boot GUID on a 32 MiB **xploader manager partition**, while a separate 32 MiB **OS boot partition** is named `boot` for Linux/TWRP. Ordinary recovery installers writing the OS by its `boot` name therefore update the OS boot partition.

On the test E6653, unmodified TWRP kernel/complete-ROM installation, system/data/cache clearing, a damaged OS boot image, and a cable-disconnected cold boot were tested with the manager surviving. SD TWRP remained available. This does **not** mean every possible ZIP or raw partition command is safe: rewriting the manager/GPT, restoring stock firmware with a PC flasher, or formatting the SD can remove the manager or its payloads. A protected recovery is an optional additional layer, not a requirement for the ordinary name-based test cases.

**Flashing a boot image alone does not create this layout.** The v1.0 installer detects the layout and preserves the existing OS boot before migrating it. Its real first-install acceptance is still pending. [Installation notes](docs/INSTALL.md) explain the difference.

An optional **v1.0 protected SD TWRP kit** is available for that exact E6653 split layout. It builds `/twrp.img` using the original publisher's TWRP userspace and the tested recovery guard kernel, with the source SD mounted read-only. See [download, build and usage instructions](recovery/guard004/README.md). Keep a stock recovery copy when you need writable SD access.

Removal is intended to use a complete matching Sony stock firmware restore through Flashtool. **The full Flashtool/GPT restoration path is not yet hardware-validated**; see the [removal notes](docs/INSTALL.md#remove-xploader--return-to-sony-stock-firmware). Ordinary recovery-flash survival is the tested scope, rather than an unbrickable-phone claim or a claim of greater durability than MAGLDR.

## Build and inspect

Linux/WSL, Python 3 and an AArch64 GNU cross compiler are used for development:

```sh
bash tools/build.sh
bash tools/check.sh
python3 tools/verify_core.py
```

To regenerate loader previews, install Pillow for your host Python and run `bash tools/render_gallery.sh`. See [building and packaging](docs/BUILD.md). A successful host build does not validate a new firmware variant or a newly built payload on hardware.

## Future plans

- A simple **Windows PC installer/updater**, similar in convenience to MAGLDR's PC installation workflow: detect the phone and layout, prepare the split boot layout, preserve the existing OS boot image, install/update the manager, and provide a recovery path.
- Simpler public first-install packaging and validation on additional E6653 firmware revisions, followed by other Z5 variants where hardware is available.
- Faster SD loading and decompression; longer USB SD transfer sessions.
- Automatic recovery covering failures at the carrier entry as well as within an OS payload.
- Better postmarketOS/Sailfish platform services, power and thermal behavior.
- Possible **Darwin/XNU** boot support, an **UEFI** handoff path, and **Windows CE / Windows NT / Windows on ARM** research. These are future research directions, not supported operating systems or release promises. Loading an executable is only one part of a platform port.
